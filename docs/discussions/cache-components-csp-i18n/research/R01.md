# R01 – next-intl 4.x and cacheComponents

Question: Does next-intl 4.x support Next 16 cacheComponents/PPR, and what setup is needed?
Scope: next-intl.dev, github.com/amannn/next-intl

## Findings
- Yes, on Next.js 16.3+ via `next/root-params`. next-intl reads `rootParams.locale()` in `i18n/request.ts`, validates with `hasLocale`, `notFound()` otherwise; stated to improve `cacheComponents` compatibility. — https://next-intl.dev/blog/nextjs-root-params (2026-08-04)
- Setup: root layout at `app/[locale]/layout.tsx`, no pass-through `app/layout.tsx`, `global-not-found` for non-localized pages, drop `setRequestLocale` (now legacy, kept for backward compatibility), keep `generateStaticParams`.
- Limits: `dynamicParams = false` does not work with Cache Components (validate at runtime + `notFound()`); `next/root-params` does not work in Route Handlers / Server Actions (pass locale explicitly).
- Known issue #2229 (next-intl 4.7.0 / Next 16.1.4): `Link` from `createNavigation` triggered a `headers()` error inside `use cache`; closed without fix ("not really reliable with 'use cache'"), workaround: pass `Link` as children. May be stale for 4.14.9 / 16.3+.
- No official example in scope; community demo https://github.com/aurorascharff/next-intl-cache-components calls `getTranslations({locale})` with explicit locale inside `use cache`.

## Conflicts
Demo uses `experimental.rootParams`; blog says native since 16.3 (blog newer).

## Confidence
Medium.
