# R04 – Smoke tests in the Japky repo (orchestrator experiment)

Scope: local build of this repo, Next 16.4.3, next-intl 4.14.9, Node 24.

## Test A – cacheComponents ON + next-intl via `next/root-params`
- Setup: `src/i18n/request.ts` reads `locale()` from `next/root-params`; root layout at `app/[locale]/layout.tsx` with `generateStaticParams`; next-intl proxy; page renders `getTranslations('Home')` and a component with `'use cache'` that calls `getTranslations({ locale, namespace })` and renders next-intl `Link`.
- `next build`: success. Routes: `○ /vi`, `○ /en` (static), `◐ /[locale]` (PPR fallback).
- `next start`: `/` → 307 to `/vi`; `/vi` HTML contains translated `<h1>`, the cached component and `<a href="/vi">` from `Link` inside `use cache`, plus `<a hrefLang="en" href="/en">`.
- Result: next-intl `Link` inside `use cache` works on 4.14.9 / Next 16.4.3. (High confidence for this setup.)

## Test B – cacheComponents OFF + nonce CSP only on `/[locale]/home`
- `next build`: `● /vi`, `● /en` (SSG via generateStaticParams), `ƒ /[locale]/home` (dynamic via `connection()`). Public pages stay static.
- Wiring a nonce through the next-intl middleware on the first attempt did not take effect (no CSP header, scripts rendered `nonce: undefined`). Composing nonce + next-intl middleware needs extra custom code; not resolved in the time box.
- Result: two-tier is feasible in principle with cacheComponents off, but costs PPR app-wide and needs custom proxy composition. (Medium confidence.)
